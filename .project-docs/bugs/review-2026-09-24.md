# Initial repository review

Reviewed on 2026-09-24 at
[`7ee47774932f5e6483495a50776e716ce58bd395`](https://github.com/AbsoluteMode/voicy/tree/7ee47774932f5e6483495a50776e716ce58bd395).
These are reviewer findings awaiting maintainer triage; none is fixed by this
documentation commit. Locations and line numbers below refer to that snapshot.

The project has a useful small-MVP boundary: a single voice room, a separate
membership API, single-use invitations, an SFU, and an installer. Invite
redemption is transactional, stored member/invite secrets are hashed, and the
API explicitly checks role order. The main obstacles to a friends-and-family
release are microphone consent/lifecycle and revocation of media access.
The advertised audio settings alone do not establish measured audio quality.

## Findings

P1 means fix before inviting ordinary users. P2 means address in the next
reliability/security iteration. Each recommendation below is proposed work.

### F1 — P1: Verify SSH host identity before sending credentials

**Location:** [deploy.rs:46–52](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src-tauri/src/deploy.rs#L46-L52), with authentication at lines 93–103.

`check_server_key` accepts every key. The fingerprint is merely logged; there
is no approval before authentication and no persisted key to compare on the
next connection. An attacker able to redirect/intercept the SSH connection can
present a different server key and receive the VPS login password. Key-based
authentication does not disclose the private key, but also does not establish
that deployment reached the intended VPS.

**Evidence:** direct inspection of the unconditional acceptance and subsequent
authentication path; no real credentials or intercepted connection were used.

**Recommendation:** verify known hosts or pin the approved key per host/port;
require a first-connection trust decision before authentication and reject
unexpected changes. Acceptance tests should cover unknown, matching and changed
keys and prove that rejected keys never reach password authentication.

### F2 — P1: Do not join with a live microphone merely on window focus

**Location:** [App.tsx:74–84](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/App.tsx#L74-L84), [handleInvite:44–50](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/App.tsx#L44-L50).

With a saved nickname, an invitation copied for forwarding is enough to join
an unfamiliar server when Voicy starts or receives focus. Clipboard detection
calls `handleInvite`, which redeems the invitation and connects immediately.
`VoiceSession` starts with `micWanted = true` and enables capture after joining.
With microphone permission already granted, this can transmit speech without
the user choosing to join that conversation. It can also interrupt their
current conversation.

**Reproduction:** save a nickname, copy a valid invitation for a server not in
the saved list, then focus Voicy. Static tracing confirms the complete path
from the focus event through membership creation to microphone activation;
Windows microphone capture was not exercised during this review.

**Recommendation:** clipboard discovery should present the server and a Join
action. Separate invitation acceptance from permission to transmit; only an
explicit join action should start the voice session. Test startup and focus
with existing microphone permission and an already active call.

### F3 — P1: Cancel pending connections and keep ownership of every room

**Location:** [voice.ts:119–139](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/lib/voice.ts#L119-L139), [voice.ts:183–207](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/lib/voice.ts#L183-L207).

While `/api/token` is pending, `this.room` is still null. Disconnecting only
clears current objects, so the late response creates a room and enables the
microphone anyway. Two overlapping calls can each pass the null check and
later create two rooms. The second completion overwrites the reference to the
first; Disconnect then closes only the currently referenced room.

**Evidence:** the [voice probes](../review-checks/voice-probes.cjs) execute the
actual transpiled `voice.ts` with deferred API responses and a fake media SDK.
They reproduced microphone enablement after cancellation and an untracked
room left enabled after two overlapping requests and a disconnect. This is
an orchestration test, not a recording or a WebRTC media test.

**Recommendation:** use a connection generation/cancellation mechanism,
validate ownership after each await, and clean up the room/context belonging
to that attempt. A stale attempt's error handler must not tear down a newer
session. Test delayed success, delayed failure, cancellation and rapid server
switches, asserting that only the current session can publish audio.

### F4 — P1: Revoking API membership does not revoke LiveKit access

**Location:** [api.rs:148–151](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/server/src/api.rs#L148-L151), [api.rs:225–232](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/server/src/api.rs#L225-L232), [livekit.rs:74–85](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/server/src/livekit.rs#L74-L85).

A modified client can keep an issued JWT and connect directly to LiveKit after
being kicked. Deleting the server through the API also leaves this path open
when the optional SSH uninstall is not performed: LiveKit permits automatic
room creation and accepts the still-valid credential. Rejecting new Voicy
token requests is insufficient.

**Evidence:** with the actual Voicy binary and `livekit/livekit-server:v1.13`
(which resolved to version 1.13.7 during the review)
in a disposable local container, the [integration probe](../review-checks/run-revocation.py)
observed all of the following:

1. Kick returned HTTP 204, and the removed member's `/api/token` returned 401.
2. The same pre-kick JWT nevertheless received a new LiveKit `JoinResponse`.
3. Server deletion returned 204 and authenticated Voicy requests returned 410.
4. The same JWT again received `JoinResponse`, recreating room `main`.

The test proves signalling admission, not an end-to-end audio transfer. The
JWT still grants microphone publication and subscription. LiveKit documents
immediate removal-related token revocation as a [Cloud feature](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/#remove-participant);
the installer uses the self-hosted server. The initial 120-second JWT lifetime
is not a complete revocation strategy: LiveKit also refreshes credentials for
connected participants, as implemented in its [v1.13.7 source](https://github.com/livekit/livekit/blob/8d11efdfcd4220092b6ac7b8a21af28526da5a6b/pkg/service/roommanager.go#L1146-L1184).

**Recommendation:** design and enforce membership revocation at media
admission, including reconnect/resume and refreshed credentials. Ensure there
is no direct signalling route that bypasses that check. Deleting a logical
server must also prevent room recreation. Keep the scenario above as an
acceptance test with the expectations reversed after implementing the fix;
do not rely only on a shorter initial TTL.

### F5 — P2: Keep the LiveKit signing secret unreadable to other VPS users

**Location:** [install.sh:136–145](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/deploy/install.sh#L136-L145).

The installer writes `LIVEKIT_API_SECRET` into `livekit.yaml` and explicitly
sets mode 0644. On an ordinary VPS installation with a traversable `/opt/voicy`
directory, any other local Unix user can read it. That user can sign their own
LiveKit join/admin tokens, bypassing Voicy membership and roles. Protecting
`.env` does not protect this second copy.

**Evidence:** static configuration and filesystem-permission analysis. This
requires local read access to the VPS; it is not an unauthenticated remote
file read. No production secret was accessed.

**Recommendation:** restrict directory/file access and grant the container's
actual runtime identity only the access it needs. Verify a clean install and
upgrade with a separate unprivileged local account; do not print file contents
in the verification log.

### F6 — P2: Keep the microphone disabled while deafened

**Location:** [voice.ts:210–225](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/lib/voice.ts#L210-L225).

Deafen first disables the microphone, but the still-enabled microphone button
calls `setMicMuted(false)`, which enables capture without checking `deafened`.
The user remains unable to hear the room while publishing speech, contradicting
the function's stated deafen behavior.

**Evidence:** the voice probe performs connect, deafen, unmute and observes
`deafened === true` with microphone publication enabled in the fake SDK.

**Recommendation:** derive effective microphone publication from both the
user's mic preference and the deafen state. Alternatively, an explicit unmute
action can also leave deafen, provided the UI/state changes together. Test the
mute/deafen combinations and restoration of the prior microphone preference.

### F7 — P2: Apply the system-default output selection to a live call

**Location:** [voice.ts:245–246](https://github.com/AbsoluteMode/voicy/blob/7ee47774932f5e6483495a50776e716ce58bd395/client/src/lib/voice.ts#L245-L246).

The settings dialog represents system default as an empty string, but
`applyAudioSettings` calls `switchActiveDevice` only for a truthy device ID.
After selecting a specific output, choosing Default changes the displayed
setting without moving the ongoing call back to the default device.

**Evidence:** the voice probe selects a named output and then Default; only
the first change reaches the SDK. This check covers dispatch to the SDK, not
Windows device routing.

**Recommendation:** explicitly apply the SDK's default output selection and
surface device-switch failures. Verify headphones to default speakers and
the reverse during an active Windows call.

The review ran on macOS. A Windows installer, WebView2 microphone permission,
real multi-device audio, packet loss, public TLS and a fresh VPS install were
not exercised. Existing GitHub build results are supplemental; they do not
test these behaviors. This is a focused repository review, not an exhaustive
security audit or a claim that every defect has been found.

To reproduce the executable checks from the repository root after `npm ci`
in `client/` and `cargo build --locked` in `server/`:

```bash
node .project-docs/review-checks/voice-probes.cjs
python3 .project-docs/review-checks/run-revocation.py
```

The integration script pins the reviewed LiveKit image by digest instead of
following the mutable `v1.13` tag. It needs Docker, Node and Python and may
download that image on first use. It publishes only a
loopback signalling port, uses generated temporary credentials and a fresh
database, and removes its container and data on exit. It changes LiveKit's
HTTP bind address inside the container so the loopback-published port is
reachable; it does not reproduce the VPS networking layout. The scripts
assert the **presence** of the reviewed defects, so successful reproduction
is not a release pass. Convert them to proper regression tests during fixes.

Documentation-specific checks passed for the added documentation and updated
README, and generated agent guidance is synchronized. The broader optional
scan of all tracked documentation/configuration did not pass: its parser
rejects existing GitHub Actions syntax/secret references and the JSONC comments
in `client/tsconfig.json`. These are pre-existing validator compatibility
issues, not evidence of leaked secrets or a failed TypeScript build; the
runtime/workflow files were left unchanged.

## Recommendations for the next milestone

1. Fix F1–F4 before distributing invitations; then cover the role matrix,
   invite replay/expiry, connection lifecycle and media revocation in CI.
2. Fix F5–F7 and exercise installation, upgrade, restart and removal on a
   disposable Debian/Ubuntu VPS. Test recovery after client credential loss.
3. Define an audio acceptance matrix using real Windows devices: headphones,
   speakers with echo cancellation, device unplugging, long calls and several
   speakers. Measure bitrate, packet loss, jitter, RTT and concealed audio;
   a configured 128 kbit/s target is not evidence of received quality.
4. Test mobile/restricted networks and decide whether TURN/TLS fallback is
   required. The current installer configures direct UDP/TCP media but no TURN
   service. Document supported networks and the server-operator trust model.
5. Publish contribution/build instructions and tested backup/restore guidance
   after those behaviors are established. Broader Discord-like features can
   follow a reliable single-room voice experience.
